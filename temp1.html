MySQL索引优化与SQL调优

  • question：B+树作为InnoDB引擎索引底层数据结构的优势是什么？为什么不用红黑树或Hash结构？
    • answer：B+树的优势：非叶子节点只存储键值不存储数据，使得单个节点能容纳更多键值，树的层级更低（通常3-4层即可支撑千万级数据），显著减少磁盘I/O次数；所有数据均存储在叶子节点，且叶子节点间形成双向链表，极大地优化了范围查询和全表扫描的性能。不选用Hash的原因：Hash索引虽支持O(1)的等值查询，但无法支持范围查询、排序及模糊匹配，且存在哈希冲突问题。不选用红黑树的原因：红黑树是二叉平衡树，每个节点只拥有两个子节点，在海量数据下树的深度极大，会导致查询时发生极其频繁的磁盘I/O操作，不符合关系型数据库基于磁盘块存储的物理特性。
  • question：什么是聚簇索引和非聚簇索引（二级索引）？什么是回表？如何通过覆盖索引（Covering Index）来避免回表？
    • answer：聚簇索引：将索引结构与整行数据存储在一起的索引，InnoDB中通常由主键充当，叶子节点保存了完整的行记录。非聚簇索引（二级索引）：叶子节点仅保存该索引列的值以及对应的主键值。回表：当通过二级索引查询数据时，由于二级索引的叶子节点不包含完整数据，需要先获取主键值，再拿着主键值回到聚簇索引中去查询完整的行记录，这个过程即为回表。覆盖索引：如果一个SQL查询所需的所有列（包括SELECT字段和WHERE条件）都包含在某个二级索引中，MySQL可直接从该索引的叶子节点返回数据，无需再回表查询聚簇索引，这种现象称为覆盖索引，能大幅提升查询性能。
  • question：深入解释索引的最左前缀匹配原则。遇到范围查询（如 >, <, between, like）时，联合索引的后续字段还会走索引吗？
    • answer：最左前缀匹配原则是指：在使用联合索引（如A, B, C）进行查询时，MySQL会从左向右严格匹配索引字段，只有使用了左侧的字段，右侧的字段才能继续走索引（可跨越无关字段但不能跳过存在字段，如查询使用A和C，只有A走索引，C不走）。遇到范围查询：当联合索引在匹配过程中遇到范围查询（>, <, between, like 'xx%'）时，当前字段可以走索引，但范围查询条件之后的后续字段将无法使用该联合索引进行B+树的快速定位过滤（在MySQL 5.6引入ICP索引下推后，后续字段可在存储引擎层进行过滤，但这属于遍历而非树查找）。如果是 >= 或 <= 且等值匹配成功，有时优化器仍能使用后续索引字段。
  • question：在实际业务中，你是如何使用 EXPLAIN 命令进行SQL调优的？重点关注其中哪几个核心字段（如 type, key, Extra）的具体取值？
    • answer：使用 EXPLAIN 加在需分析的SQL前，主要通过分析执行计划来评估索引使用情况。重点关注字段：1. type（访问类型）：表明扫描表的方式，性能由好到差依次为 system > const > eq_ref > ref > range > index > ALL，调优目标至少达到 range 级别，最好达到 ref。2. key：实际使用的索引，若为NULL则说明全表扫描或索引失效。3. Extra（附加信息）：关注是否出现性能杀手如 Using filesort（使用了外部文件排序，需优化索引以利用树的有序性）或 Using temporary（使用了临时表，常见于GROUP BY/DISTINCT，极耗性能）；若出现 Using index 则表明触发了覆盖索引，性能极佳；出现 Using index condition 说明触发了索引下推（ICP）。
  • question：请列举至少五种常见的索引失效场景，并从B+树底层数据结构的角度剖析其失效的根本原因。
    • answer：1. 左模糊匹配（如 LIKE '%abc'）：B+树是严格按索引列的值从左到右有序排列的，左侧字符未确定导致无法利用树形结构二分查找。2. 对索引列使用函数或计算（如 WHERE YEAR(date) = 2023）：B+树中存储的是原始数据的值，经过函数或运算后的结果在树中无序，只能全表扫描。3. 隐式类型转换（如字符串类型字段传入数字 WHERE str_col = 123）：MySQL优化器会自动在列上套用 CAST 函数将其转为数字再比较，等同于对列使用了函数。4. 联合索引违背最左前缀原则（如联合索引(A,B)，直接 WHERE B=1）：B+树是先按A排序，A相同时再按B排序。跳过A直接查B，B在整棵树中是无序的。5. OR条件中包含非索引列：若OR连接的两个条件中有一侧没有索引，优化器评估后认为即便一侧走索引另一侧仍需全表扫描，不如直接全表扫描成本更低，从而导致整体索引失效。
  • question：面对一张千万级数据量且存在深分页查询（如 LIMIT 1000000, 10）的慢SQL，你的优化方案是什么？
    • answer：深分页的核心痛点在于：MySQL会通过二级索引（或全表扫描）提取1,000,010条记录，进行回表操作获取全量数据后，再丢弃前1,000,000条记录，返回最后的10条，导致大量无效的随机I/O。优化方案：1. 延迟关联（子查询优化）：先通过覆盖索引（不回表）快速分页查出目标数据的10个主键ID，再将这10个ID与原表进行INNER JOIN获取完整行数据（SELECT * FROM t INNER JOIN (SELECT id FROM t ORDER BY create_time LIMIT 1000000, 10) AS temp ON t.id = temp.id），将回表次数从100万次锐减至10次。2. 游标/游标分页法（Seek Method）：若查询为顺序翻页且主键/排序字段连续递增，可记录上一页最后一条记录的ID，下一页直接通过条件过滤（WHERE id > last_max_id ORDER BY id LIMIT 10），彻底避开深分页问题，效率最高。
