# **Java编程语言及面向对象**
* question：面向对象的三大特性是什么？能结合实际业务代码谈谈你的理解吗？
    * answer：封装、继承、多态。封装用于隐藏实现细节暴露接口（例如实体类私有化字段并提供getter/setter，保护数据一致性）；继承用于代码复用并抽取共性（例如抽取包含创建时间、更新时间的BaseEntity基类）；多态用于实现同一接口的不同策略（例如定义PayService接口，由WechatPayServiceImpl和AliPayServiceImpl分别实现，运行时根据条件动态绑定，符合开闭原则）。
* question：重载（Overload）和重写（Override）有什么区别？
    * answer：重载发生在本类中，方法名必须相同但参数列表（类型、个数、顺序）不同，与返回值无关，属于编译时多态；重写发生在父子类（或接口与实现类）中，方法签名（方法名+参数列表）必须相同，返回值和抛出异常范围需小于等于父类，访问修饰符需大于等于父类，属于运行时多态。
* question：接口和抽象类有什么本质区别？在实际系统设计中如何选择？
    * answer：本质区别：抽象类是对事物的抽象（is-a），支持单继承，可包含普通成员变量、构造器和具体实现方法；接口是对行为的规范（like-a），支持多实现，JDK8前仅能包含抽象方法和常量。选择原则：当需要定义通用骨架并复用部分代码时选用抽象类（模板方法模式）；当需要定义标准规范、扩展不同层级类的附加能力时选用接口（策略模式）。
* question：String、StringBuffer和StringBuilder的区别与底层实现原理是什么？
    * answer：String是不可变类，底层封装了被final修饰的数组（JDK9前为char[]，JDK9后为byte[]），每次字符串修改都会生成新对象；StringBuffer和StringBuilder是可变类，底层数组无final修饰，容量不足时会进行动态扩容（通常为原容量2倍+2）并在原地修改。两者的区别在于StringBuffer的修改方法由 `synchronized` 修饰，线程安全但性能较低；StringBuilder非线程安全，但单线程环境下性能最高。
* question：HashMap的底层数据结构是什么？它是如何解决哈希冲突的？详细描述其扩容机制。
    * answer：JDK1.8中底层数据结构为数组+链表+红黑树。解决冲突采用链地址法，发生哈希冲突时将元素插入链表尾部；当链表长度大于8且数组总容量大于等于64时，链表转化为红黑树以优化查询。扩容机制：当容器内元素数量大于“容量 × 负载因子（默认0.75）”时触发扩容，新数组容量为旧数组的2倍。JDK1.8优化了数据迁移过程，通过检查节点hash值参与运算的最高位是0还是1，直接决定元素保留在原索引处还是移动到“原索引 + 旧数组容量”的新位置，避免了重新计算哈希。
* question：ConcurrentHashMap在JDK1.7和1.8中有哪些结构设计上的区别？
    * answer：JDK1.7采用基于ReentrantLock的Segment分段锁+HashEntry数组+链表结构，并发粒度为Segment（默认16段），存在并发瓶颈；JDK1.8彻底抛弃Segment，采用与HashMap相同的Node数组+链表+红黑树结构，将锁粒度细化至每个哈希桶的首节点，通过CAS操作 + `synchronized` 保证并发安全，大大降低了锁冲突概率，并在高冲突场景下利用红黑树提升了查询效率。


# **JVM内存模型与类加载机制**
* question：请详细描述JVM的运行时数据区，哪些区域是线程私有的，哪些是共享的？
    * answer：运行时数据区包括：程序计数器、Java虚拟机栈、本地方法栈、Java堆、方法区（JDK1.8后实现为元空间）。**线程私有区域**：程序计数器（记录当前线程执行的字节码指令地址）、虚拟机栈（存储局部变量表、操作数栈、动态链接、方法出口等）、本地方法栈（为Native方法服务）。**线程共享区域**：Java堆（存放对象实例和数组，是垃圾收集的主要区域）、方法区（存储已被加载的类信息、常量、静态变量、即时编译器编译后的代码等）。
* question：什么是Java内存模型（JMM）？它主要解决了并发编程中的什么问题？
    * answer：JMM（Java Memory Model）是Java虚拟机规范中定义的一种抽象的内存模型，用于屏蔽各种硬件和操作系统的内存访问差异，定义了程序中各种变量（线程共享变量）的访问规则。它主要解决了并发编程中的三大核心问题：**可见性**（保证一个线程对共享变量的修改对其他线程立即可见）、**原子性**（保证特定操作序列不可被中断）、**有序性**（通过禁止特定类型的编译器和处理器指令重排序来保证执行顺序）。
* question：volatile关键字的作用是什么？它的底层原理（内存屏障）是如何实现的？
    * answer：作用：保证被修饰变量的内存可见性，并禁止指令重排序优化，但不保证复合操作的原子性。底层原理：基于汇编指令的 `lock` 前缀和内存屏障（Memory Barrier）实现。在写 `volatile` 变量时，会在写操作后插入Store Barrier（写屏障），强制将线程本地工作内存中修改后的数据刷新到主内存；在读 `volatile` 变量时，会在读操作前插入Load Barrier（读屏障），强制使本地工作内存中的缓存失效，直接从主内存读取最新值。同时，内存屏障会阻止屏障两侧的指令进行越界重排序。
* question：描述一下Java的类加载完整过程（加载、验证、准备、解析、初始化）。
    * answer：1. **加载**：通过类的全限定名获取定义此类的二进制字节流，转化为方法区的运行时数据结构，并在堆中生成对应的 `java.lang.Class` 对象。2. **验证**：确保Class文件的字节流包含信息符合当前虚拟机规范要求（包括文件格式、元数据、字节码和符号引用验证），保证系统安全。3. **准备**：为类变量（静态变量）在方法区分配内存并设置初始零值。4. **解析**：将常量池内的符号引用替换为直接引用（内存地址或偏移量）。5. **初始化**：执行类构造器 `<clinit>()` 方法，根据程序员通过程序制定的主观计划去初始化类变量和其他资源（执行静态代码块和静态变量赋值）。
* question：什么是双亲委派模型？为什么要这样设计？
    * answer：双亲委派模型是指：当一个类加载器收到类加载请求时，它首先不会自己尝试去加载这个类，而是将请求委派给父类加载器去完成，依次向上一直委派到顶层的启动类加载器（Bootstrap ClassLoader）。只有当父加载器在它的搜索范围中找不到该类时，子加载器才会尝试自己去加载。设计原因：**保证基础类的安全性与全局唯一性**，防止核心API（如 `java.lang.Object`）被用户自定义的同名类篡改或覆盖。
* question：Tomcat或JDBC的SPI机制是如何打破双亲委派模型的？
    * answer：**JDBC的SPI机制**：核心接口（如 `java.sql.Driver`）由启动类加载器加载，但具体的数据库驱动实现类在第三方厂商的Jar包中，启动类加载器无法触及。因此，DriverManager通过获取**线程上下文类加载器**（Thread Context ClassLoader，通常是Application ClassLoader）来加载具体的驱动实现类。这是一种父类加载器请求子类加载器完成类加载的行为，打破了双亲委派自下而上的委派规则。**Tomcat**：为了实现不同Web应用之间的类库隔离，Tomcat自定义了 `WebappClassLoader` 并重写了 `loadClass` 方法。它会优先加载当前Web应用目录（`/WEB-INF/classes` 和 `/WEB-INF/lib`）下的类，如果找不到再委派给父类加载器，这直接颠覆了双亲委派中“优先委派给父类”的逻辑。

# **GC算法与垃圾回收器**

* question：JVM是如何判断一个对象是否可以被回收的？GC Roots具体包含哪些类型的对象？
    * answer：JVM主要通过**可达性分析算法**（Reachability Analysis）来判断对象是否存活。以GC Roots为起始点，根据引用关系向下搜索，搜索走过的路径称为引用链（Reference Chain）。如果某个对象到GC Roots间没有任何引用链相连，则证明此对象不可用，可以被回收。GC Roots主要包含以下类型：虚拟机栈（栈帧中的本地变量表）中引用的对象、方法区中类静态属性引用的对象、方法区中常量引用的对象、本地方法栈中JNI（即Native方法）引用的对象、Java虚拟机内部的引用（如基本数据类型对应的Class对象、常驻异常对象等）、所有被同步锁（synchronized）持有的对象。
* question：详细对比标记-清除、标记-复制、标记-整理三种核心垃圾回收算法的优缺点。
    * answer：1. **标记-清除（Mark-Sweep）**：分为标记存活对象和清除死亡对象两个阶段。优点是实现简单，不需要移动对象；缺点是执行效率不稳定（随对象数量增长而降低），且会产生大量不连续的内存碎片。2. **标记-复制（Mark-Copy）**：将内存按容量划分为大小相等的两块，每次只使用其中一块。存活对象复制到另一块，再清理已使用过的内存。优点是实现简单、运行高效、无内存碎片；缺点是可用内存缩减为原来的一半（或需配合Survivor区调配），且在对象存活率较高时复制开销极大。3. **标记-整理（Mark-Compact）**：标记过程与“清除”算法一样，但后续将所有存活对象向内存空间一端移动，然后直接清理掉边界以外的内存。优点是无内存碎片，内存利用率高；缺点是移动存活对象并更新引用是一项极重的操作，必须暂停用户线程（Stop The World），效率最低。
* question：讲一讲CMS垃圾回收器的工作流程，它可能会引发什么严重问题（如Concurrent Mode Failure）？
    * answer：CMS（Concurrent Mark Sweep）是一种以获取最短回收停顿时间为目标的回收器。工作流程分为四个步骤：**初始标记**（STW，仅标记GC Roots能直接关联的对象，速度极快）、**并发标记**（与用户线程并发执行，进行整个GC Roots Tracing）、**重新标记**（STW，修正并发标记期间因用户程序继续运行而导致标记变动的那一部分记录）、**并发清除**（与用户线程并发执行，清理死亡对象）。可能引发的严重问题：**Concurrent Mode Failure（并发模式失败）**。由于CMS在并发清理阶段用户线程仍在运行，会产生新的“浮动垃圾”，且CMS基于标记-清除算法会产生内存碎片。当老年代没有足够连续空间分配给大对象，或者老年代预留的空间无法满足并发期间程序的分配需求时，就会触发该错误，导致JVM临时冻结用户线程，退化使用Serial Old收集器进行老年代的完全STW垃圾收集，造成极长的停顿。
* question：G1垃圾回收器的内存划分和回收过程是怎样的？它与CMS的最大区别是什么？
    * answer：**内存划分**：G1打破了传统的物理分代，将整个Java堆划分为多个大小相等的独立区域（Region），每个Region可以根据需要扮演Eden、Survivor或Old空间，此外还有专门存储大对象的Humongous区域。**回收过程**：包含年轻代GC（Young GC）、并发标记周期（初始标记、根区域扫描、并发标记、最终标记、清理阶段）和混合收集（Mixed GC，回收所有年轻代和部分回收价值最高的老年代Region）。**与CMS的最大区别**：1. **空间整合**：G1整体基于“标记-整理”算法，局部（两个Region之间）基于“复制”算法，不会产生内存碎片。2. **可预测的停顿**：G1建立可预测的停顿时间模型，能够让使用者明确指定在一个长度为M毫秒的时间片段内，消耗在垃圾收集上的时间不得超过N毫秒，G1会根据此目标优先回收价值收益最大的Region。
* question：什么是跨代引用？JVM是如何通过记忆集（Remembered Set）和卡表（Card Table）解决跨代引用问题的？
    * answer：**跨代引用**是指某个内存区域（如老年代）中的对象引用了另一个内存区域（如新生代）中的对象。在进行Minor GC时，为了确定新生代对象是否存活，除了扫描年轻代的GC Roots，还必须扫描老年代来排查跨代引用，这会导致全堆扫描，效率极低。**解决方案**：JVM引入了**记忆集**（Remembered Set）这种数据结构，用于记录从非收集区域指向收集区域的指针集合。**卡表**（Card Table）是记忆集的具体实现方式。它将堆内存划分成一个个大小固定的内存块（卡页，Card Page），并维护一个字节数组（卡表）。如果某个卡页内的对象存在跨代引用（如老年代对象引用了新生代对象），则将卡表数组对应的元素标记为1（称为“脏卡”）。发生Minor GC时，垃圾收集器只需扫描卡表中被标记为“脏卡”的内存区域，从而避免了扫描整个老年代，大幅提升了GC效率。


# **JVM调优与问题排查**
* question：线上系统CPU突然飙升到100%，请给出你完整的排查和定位思路。
    * answer：1. 使用 `top -c` 定位CPU占用最高的Java进程ID（PID）。2. 使用 `top -Hp <PID>` 定位该进程下CPU占用最高的线程ID（TID）。3. 将十进制的TID转换为十六进制（执行 `printf "%x\n" <TID>`）。4. 使用 `jstack <PID> | grep -A 20 <十六进制TID>` 提取该线程的堆栈信息。5. 分析堆栈日志：若是业务线程，则直接定位具体业务代码行数（排查死循环、复杂正则表达式、频繁自旋死锁等）；若是GC线程，则说明系统可能在频繁发生Full GC导致CPU资源被回收线程耗尽，需转入OOM或GC排查流程。
* question：如何排查和解决线上系统频繁发生Full GC的问题？
    * answer：1. 收集GC表现：使用 `jstat -gcutil <PID> 1000` 观察各区域内存使用率和GC频率，或查看GC日志。2. 确认Full GC触发原因：如果老年代使用率持续上升且Full GC后不下降，说明存在内存泄漏或大对象持续分配；如果是元空间（Metaspace）频繁扩容或主动调用 `System.gc()` 也会触发。3. 导出Dump快照：执行 `jmap -dump:live,format=b,file=heap.bin <PID>`。4. 离线分析：使用MAT（Memory Analyzer Tool）加载Dump文件，通过Dominator Tree（支配树）和Histogram（直方图）查找Retained Heap最大的对象，顺着GC Roots引用链定位到具体的泄漏类和代码。5. 修复与调优：修复代码逻辑，或调整JVM参数（如增大老年代空间、调大元空间初始值 `-XX:MetaspaceSize` 避免早期频繁扩容）。
* question：如果发生OOM（Out of Memory），你通常的处理流程和使用的排查分析工具是什么？
    * answer：1. 保护现场：依赖JVM启动时配置的 `-XX:+HeapDumpOnOutOfMemoryError` 和 `-XX:HeapDumpPath` 参数自动生成的Heap Dump文件，并保留当时的系统监控图表。2. 快速恢复：将故障节点从网关/负载均衡摘除，保留现场（或直接重启服务）以快速恢复线上业务。3. 定位OOM类型：查看日志确认是 `Java heap space`（堆内存溢出）、`Metaspace`（元空间溢出）、还是 `unable to create new native thread`（无法创建新线程）。4. 深度分析：使用MAT或JProfiler加载Dump文件，分析对象的保留集（Retained Set），排除弱引用和软引用，追踪强引用链至GC Roots，定位导致内存溢出的具体对象（如未分页的巨量数据库查询结果、未清理的ThreadLocal变量等）。5. 验证：在测试环境复现并压测修复后的代码。
* question：请列举你熟悉的JVM调优核心参数及其实际应用场景（如-Xms, -Xmx, -Xmn, -XX:MetaspaceSize等）。
    * answer：1. `-Xms` 和 `-Xmx`：设置堆的初始和最大内存。场景：通常设置为相同值（如 `-Xms4g -Xmx4g`），以避免应用运行期间堆内存频繁扩容和收缩带来的系统抖动与性能开销。2. `-Xmn`：设置年轻代大小。场景：直接影响Minor GC的频率和对象晋升老年代的概率，高并发短生命周期对象多的场景需适当调大。3. `-XX:MetaspaceSize`：设置元空间初始大小。场景：默认值通常较小（约21MB），应用启动时加载大量类极易触发Full GC进行扩容，建议线上环境直接调大（如设为256M）。4. `-XX:MaxTenuringThreshold`：对象晋升老年代的年龄阈值。场景：针对存在较多中等生命周期对象的场景，可适当调大以将其留在年轻代被清理，减轻老年代压力。5. `-XX:+UseG1GC`：启用G1垃圾收集器。场景：适用于大内存（通常超8G）且对停顿时间（`-XX:MaxGCPauseMillis`）有严格要求的系统。
* question：在实际项目中，你最常用哪些命令或工具（如jstack, jmap, jstat, Arthas等）来定位内存泄漏问题？
    * answer：1. **jstat**：通过 `jstat -gc <PID>` 实时监控GC状态，若发现老年代内存（O列）持续增长且Full GC（FGC列）次数飙升，初步判定存在泄漏。2. **jmap**：通过 `jmap -histo:live <PID>` 快速在线查看内存中实例数量最多、占用最大的类，辅助快速定位；或用于生成dump文件。3. **Arthas（阿尔萨斯）**：线上排查利器。常用命令组合：使用 `dashboard` 实时总览系统整体的CPU、内存和线程状况；遇到内存飙升时，使用 `heapdump` 导出快照；如果伴随CPU升高，使用 `thread -n 3` 抓取最耗CPU的线程堆栈；针对疑似引发泄漏的方法，使用 `watch` 或 `trace` 动态观测方法的入参、返回值及执行耗时，无需重启服务即可完成深度诊断。
